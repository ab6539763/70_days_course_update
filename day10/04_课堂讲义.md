## 第一章 · import 机制（09:00–10:30）

### 1.1 模块 vs 包

| 概念 | 是什么 | 例子 |
|------|--------|------|
| **模块** | 一个 `.py` 文件 | `exceptions.py` |
| **包** | 含 `__init__.py` 的目录 | `sparktech/`、`sparktech/utils/` |
| **命名空间包** | 无 `__init__.py` 也可（PEP 420） | 今日不展开，公司规范仍要求 `__init__.py` |

```python
import sparktech              # 加载 sparktech/__init__.py
from sparktech import validate_phone
from sparktech.utils import load_json_file
```

### 1.2 模块搜索顺序

Python 按顺序在以下路径查找 `sparktech`：

1. 内置模块  
2. `sys.path` 中的目录（含当前脚本目录、虚拟环境 `site-packages`）  
3. `PYTHONPATH` 环境变量  

教学入口脚本中的惯例：

```python
import sys
from pathlib import Path
sys.path.insert(0, str(Path(__file__).resolve().parent))
```

> **讲师强调**：这是 **教学捷径**。Day 12 用 `pip install -e .` 后应删除。

### 1.3 `__init__.py` 做什么

1. 把目录标记为包  
2. 执行包级初始化代码（宜简短）  
3. 通过 `from .utils import ...` **重导出**公开 API  

打开 [code/sparktech/__init__.py](./code/sparktech/__init__.py)：

```python
__version__ = "0.1.0"
__all__ = ["validate_phone", "ValidationError", ...]
```

`__all__` 控制 `from sparktech import *` 导出哪些名字（团队规范：显式 import 为主，`__all__` 作文档）。

### 1.4 绝对导入 vs 相对导入

```python
# 包内 validators.py — 绝对导入（推荐）
from sparktech.exceptions import ValidationError

# 包内 utils/__init__.py — 相对导入
from .validators import validate_name
from .io import load_json_file
```

| 方式 | 适用 |
|------|------|
| `from sparktech.xxx` | 包内、包外均可，清晰 |
| `from .xxx` | 仅包内部，重构目录时更稳 |

**反面教材**：直接 `python sparktech/utils/validators.py` → `ImportError: attempted relative import with no known parent package`。  
**正确**：`python demo_imports.py` 或 `python -m sparktech`（需包可运行设计）。

## 第二章 · `if __name__ == "__main__"`（10:30–11:30）

### 2.1 原理

每个模块都有 `__name__`：

- 被 **直接运行**：`__name__ == "__main__"`  
- 被 **import**：`__name__ == "模块名"`（如 `"demo_imports"`）

```python
def main() -> None:
    print("只有直接运行才执行")

if __name__ == "__main__":
    main()
```

### 2.2 为何需要 guard

| 没有 guard | 有 guard |
|------------|----------|
| import 时副作用执行（print、删文件） | import 只加载定义 |
| 测试无法干净导入 | `verify_package.py` 可 import 被测模块 |

### 2.3 `python script.py` vs `python -m module`

```bash
python3 demo_imports.py      # __name__ = __main__
python3 -m demo_imports        # 同上，但 sys.path[0] 为当前目录而非脚本目录
```

今日在 `code/` 目录下两者等价；Day 14 多模块项目更推荐 `-m`。

▶ 运行：`cd day10/code && python3 demo_imports.py`

## 第三章 · 下午前半：异常处理（14:00–15:30）

### 3.1 try / except / else / finally

```python
try:
    result = json.loads(text)      # 可能抛 JSONDecodeError
except json.JSONDecodeError as exc:
    print(f"解析失败: {exc}")      # 仅异常时
else:
    print(f"成功: {result}")       # 仅无异常时
finally:
    print("总会执行")              # 清理：关文件、释放锁
```

| 子句 | 执行条件 |
|------|----------|
| `try` | 进入受保护代码块 |
| `except` | 匹配到异常类型 |
| `else` | **没有**异常时 |
| `finally` | **总是**（除非进程被杀） |

### 3.2 捕获顺序：从具体到泛化

```python
try:
    ...
except ValidationError:      # 子类先
    ...
except SparkTechError:       # 父类后
    ...
except Exception:            # 兜底，慎用
    ...
```

`ValidationError` 是 `SparkTechError` 子类；若顺序反了，子类分支永远进不去。

### 3.3 自定义异常

见 [code/sparktech/exceptions.py](./code/sparktech/exceptions.py)：

```python
class ValidationError(SparkTechError):
    def __init__(self, message: str, *, field: str = "") -> None:
        super().__init__(message, code="VALIDATION_ERROR")
        self.field = field
```

**好处**：

- 调用方按类型分支  
- 附带 `field`、`path` 等上下文  
- 统一 `code` 便于日志与监控  

### 3.4 raise：主动抛出与 re-raise

```python
# 校验失败
if not name.strip():
    raise ValidationError("姓名不能为空", field="name")

# 包装后保留链
try:
    load_json_file(path)
except DataLoadError:
    log(path)
    raise   # 等价 raise 当前异常，保留 __cause__
```

### 3.5 业务代码示范

`validators.py` 不写 `print`，只 `raise`：

```python
def validate_phone(phone: str, *, min_digits: int = 7) -> str:
    digits = normalize_phone(phone)
    if len(digits) < min_digits:
        raise ValidationError(
            f"手机号至少 {min_digits} 位数字，当前 {len(digits)} 位",
            field="phone",
        )
    return digits
```

CLI 层再 `try/except` 转成用户友好提示——**库层与展示层分离**。

▶ 运行：`python3 demo_exceptions.py`

## 第四章 · 下午后半：venv、pip、requirements（15:30–16:30）

### 4.1 为何需要虚拟环境

| 问题 | venv 解法 |
|------|-----------|
| 项目 A 要 `requests==2.28`，项目 B 要 `2.32` | 各项目独立 `.venv` |
| `pip install` 污染系统 Python | 包装到 `.venv/lib/...` |
| 新人环境不一致 | `requirements.txt` 可复现 |

### 4.2 标准工作流

```bash
cd day10/code

# 方式一：脚本（推荐）
bash setup_venv.sh

# 方式二：手动
python3 -m venv .venv
source .venv/bin/activate    # Windows: .venv\Scripts\activate
python -m pip install --upgrade pip
pip install -r requirements.txt
```

激活后命令行提示符前会出现 `(.venv)`，`which python` 应指向 `.venv/bin/python`。

### 4.3 requirements.txt 写法

```
requests>=2.31.0,<3
python-dotenv>=1.0.0,<2
```

| 符号 | 含义 |
|------|------|
| `==1.2.3` | 精确版本 |
| `>=1.0,<2` | 兼容范围（推荐） |
| 无版本 | 不推荐，不可复现 |

常用命令：

```bash
pip install -r requirements.txt
pip freeze > requirements.lock   # 锁定精确版本（选讲）
pip show requests
pip list
```

### 4.4 `.gitignore` 提醒

```
.venv/
__pycache__/
*.pyc
.env
```

`.env` 存密钥，**永不提交**；`python-dotenv` 仅在本地加载。

## 第六章 · 常见错误与排错

| 现象 | 原因 | 解决 |
|------|------|------|
| `ModuleNotFoundError: sparktech` | 未加 `code/` 到 path | 入口脚本 `sys.path.insert` 或激活 venv 后 editable install |
| `ImportError: attempted relative import` | 直接运行包内 `.py` | 用入口脚本或 `python -m` |
| `except` 子句进不去 | 异常类型不匹配 | 检查继承关系与顺序 |
| `pip` 装到系统 Python | 未激活 venv | `source .venv/bin/activate` |
| `JSONDecodeError` 未转业务异常 | 未包装 | `io.py` 里 catch 后 `raise DataLoadError` |
| 裸 `except:` | 吞掉 `KeyboardInterrupt` | 写 `except Exception` 或具体类型 |
