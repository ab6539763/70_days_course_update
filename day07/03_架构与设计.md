# Day 7 架构与设计 · 通讯录数据流与模块划分

## 1. 总体架构

```text
┌─────────────────────────────────────────────────────────────────┐
│                    address_book.py（单文件 v1.0）                  │
│  ┌─────────────┐   ┌──────────────┐   ┌────────────────────────┐ │
│  │ persistence │   │   service    │   │          cli           │ │
│  │ load/save   │──▶│ CRUD/search  │◀──│ menu + handlers      │ │
│  └──────┬──────┘   └──────┬───────┘   └────────────────────────┘ │
└─────────┼─────────────────┼───────────────────────────────────────┘
          │                 │
          ▼                 ▼
   contacts.json      contacts: list[dict]
                       next_id: int
```

**设计原则**（张工规范）：

1. **单一数据源**：内存中仅 `contacts` 列表为真；文件是快照。  
2. **修改走函数**：不散落 `contacts[i]["name"] = ...` 在 CLI 里。  
3. **Day 8 可演进**：`service` 层函数将迁入 `ContactBook` 类方法。

## 2. 数据流（端到端）

```mermaid
flowchart TD

    M --> N
```

## 4. 为何用 list 而不是 dict[id]？

| 方案 | 优点 | 缺点 |
|------|------|------|
| `list[dict]` | 与 Day 4 待办一致；JSON 自然序列化为数组；便于排序遍历 | 按 id 查找 O(n) |
| `dict[int, dict]` | 按 id 查找 O(1) | Week 1 未系统讲授；JSON 需额外转换 |

**v1.0 选择 list**：培训重点在 CRUD 流程与 JSON，数据量 < 1000 时线性查找足够。Day 8 可在类内部改用 `dict` 索引优化。

## 5. next_id 持久化设计

```text
  添加前: next_id = 5  →  新记录 id=5  →  next_id 变为 6
  保存时: JSON 写入 "next_id": 6
  重启后: load 读到 6，下一条 id 仍为 6
```

若只保存 `contacts` 不保存 `next_id`，删除最大 id 后重启会导致 **id 冲突**。

## 6. JSON 序列化决策

| 决策 | 选择 | 原因 |
|------|------|------|
| 缩进 | `indent=2` | HR 可人工查看 |
| 中文 | `ensure_ascii=False` | 姓名部门可读 |
| 时间 | UTC ISO 字符串 | 避免时区对象 JSON 不可序列化 |
| 版本 | 顶层 `version` | 日后 Day 11 迁移 schema |

## 7. 错误处理策略

| 场景 | 行为 |
|------|------|
| 文件不存在 | 空列表启动，首次 save 创建文件 |
| JSONDecodeError | 打印行号信息，以空列表继续（或讲师版要求退出） |
| 校验失败 | `ValueError` 捕获，打印原因，不中断主循环 |
| Ctrl+C | `KeyboardInterrupt` 友好提示 |
